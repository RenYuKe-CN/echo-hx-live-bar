# 美团券码自助核销接入

## 适用范围与上线前配置

本项目接入**到店餐饮 → 餐饮品牌直连 → 直连团购核销，businessId=79**，顾客在本店微信小程序输入美团数字券码，查询一个固定套餐，确认后核销并生成桌台配送订单。没有接入顾客账号 OAuth 查询全部已购券的 businessId=33，也不使用旧版 clientId/clientSecret 代替直连凭证。

开发代码与模拟接口测试已经完成，**尚未做真实商户、实券或微信真机联调**。美团文档标注此组接口“无需业务授权”，请求不传 `appAuthToken`；这不代表匿名可调用或普通商家账号能直接使用。仍须在美团技术服务合作中心取得对应直连能力、developerId / SignKey，并完成收银门店与美团门店绑定。上线前需向美团对接方确认本店行业与顾客自助场景支持此组接口。

超级管理员在“接口配置”填写以下字段，也可通过服务器环境变量注入（环境变量优先）：

| 环境变量 | 用途 |
| --- | --- |
| `MEITUAN_DEVELOPER_ID` | 开通餐饮品牌直连能力的开发者 ID |
| `MEITUAN_SIGN_KEY` | 服务端签名密钥，绝不下发小程序 |
| `MEITUAN_VENDOR_SHOP_ID` | **已完成美团绑定**的本店收银门店编号，不能填桌号，也不能随意用美团 poiId 代替 |
| `MEITUAN_ERP_ID` | 美团核销请求中的收银 ERP 账号 ID |
| `MEITUAN_ERP_NAME` | 对应账号名称 |
| `MEITUAN_REDEMPTION_ENABLED` | 默认 `0`；完成权限、门店、套餐配置与实券验收后设为 `1` |

配置完整性检查只核对是否填写，不能证明凭证有效、接口权限开通或门店绑定成功。开发阶段使用独立测试环境启用，不直接用生产券试验。保留人工商家端核销后录入配送的入口。

## 套餐映射

1. 本地“商品与库存”建立组合套餐，配置每套的基础货品和数量、售价、进货成本与附加成本。
2. 美团**直连团单与收银菜品配置**将该固定套餐关联为一个整套收银 SKU，`dealSkuMappingDetail.count=1` 且 `vendorSkus` 只有一个 ID。这个 SKU 代表整套商品，本地再展开实际货品出库。远端关系需要通过美团已开通的配置流程建立；本项目的本地映射不会自动同步到美团。
3. 本地“团购套餐映射”选美团，将接口 `dealId` 关联本店组合套餐。可选 SKU 字段填与远端 `vendorSkus[0]` 相同的收银 SKU ID；留空时按团单 ID 匹配。没有映射或 SKU 不匹配不能核销，不按套餐名字猜测。
4. 每次查询只对应顾客输入的**一张券**。查询返回的 `count` 是同一购券订单的剩余券数，不能据此一次配送多套。

当前只支持普通固定套餐券 `dealType=2`。不处理代金券、免费试券、阶梯 / 普通次卡、一键买单券、商企通券或多选套餐。平台返回的有效期和张数上限会展示、校验；本流程每次兑换一张券。`dealRuleCouponLimit` 没有明确描述为每桌限制，不额外推断成整桌累计限用规则；美团预核销和正式核销负责最终资格校验。

美团 `realAmount` 是文档定义的商家实收估算金额（手续费未扣除），存为团购收入，不能标成真实到账金额；真实结算继续由超级管理员另行录入。`dealValue` 是套餐面额，用于远端整套 SKU 的 `unitPrice` 与订单 `toPayAmount`，两者保持相等。本地套餐售价与参考团购售价不覆盖平台核销返回的金额。

## 请求与订单流程

所有美团请求均由服务端向固定官方 HTTPS 地址发送表单 POST：`https://api-open-cater.meituan.com/dishconnect/tuangou/coupon/`。公共参数固定 `businessId=79`、`version=2`、UTF-8、秒级时间戳；`biz` 为完整 JSON 字符串。签名为 `SHA1(SignKey + 按字典序拼接的非空参数名和值)`，签名时不做 URL 编码，发送时做表单编码。平台超长数值 ID 按字符串解析，券码保留前导零。

1. **查询**调用 `status/query`，要求 `status=10`、`couponStatus=10`、普通固定套餐、明确金额与整套 SKU。保存券、套餐组成、门店与金额快照，有效查询窗口 5 分钟，尚未核销或出库。
2. **确认**再次检查桌台、归属、有效期、单次用券上限与所有组成货品的可售库存。原子预占货品，并保存稳定的 `GBMT…` 商家订单号、幂等键和核销参数，随后才调用平台。
3. 再查券状态 / ID / SKU / 金额，调用 `batchPrepare` 校验条件，再调用 `batchConsume` 核销单张券。预核销没有实际消耗券，本版本不请求远端锁券。
4. 只有 `OP_SUCCESS` 且回执中包含**恰好这张券**、金额一致才认定成功。该接口没有独立 `verify_id`，保存商家订单号、核销券和平台 `traceId` 作为证据，不编造平台凭证号。
5. 先持久化成功证据，再原子生成同号配送订单、展开本地基础货品、结转预占并出库。服务工作台收到现有订单事件。重复确认 / 恢复不会重复核销、扣库或配送。

## 超时、恢复与撤销

- 正式核销**尚未发出**时的查券 / 预核销失败标为未完成，释放本次本地库存预占，顾客可以重新查询。
- 正式请求发出后，超时、缺失回执、错误回执或服务器中断均保留为待核对，继续预占，不再自动发送 `batchConsume`。接口返回“已使用”本身不能证明是本店这笔订单核销成功。
- 定时任务每分钟核对一批美团待确认记录；管理员可点“查询美团结果”。调用 `queryLocalListByDate`，使用原门店、原核销日期和**原商家订单号**查询；为覆盖验券跨午夜，再核对上海时区次日。只接受该订单中套餐 ID、券码、`couponStatus=10`（历史接口中表示已核销）与实收金额一致的记录。确认后复用原快照生成订单。
- 历史为空、仍不明确、金额不一致、已撤销、在别的订单核销或查询失败都不会自动释放库存或生成配送。管理员仍可核对实际平台记录并人工处理。美团接口支持 180 天内直连历史，其他平台核销记录不在该历史接口范围内。
- 修改 developerId 或门店配置后，旧记录须先核对原门店，不用新门店的结果结算旧记录。并行核对与人工处理都使用条件状态更新；已处理记录不被迟到响应覆盖。
- 原平台撤销 / 退款仍由商家先操作，再通过现有后台同步退库；此版本不新增自动平台撤销。已有配送或配送在途的套餐需按实际交付人工处理。
